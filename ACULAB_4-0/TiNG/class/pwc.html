Prosody with classes

All Prosody basic APIs are defined using only the C language. For C++ programs, it is much nicer to use a C++ API, but there is no official Aculab C++ API. Here is a C++ API for Prosody which is built mostly automatically from the same master specification that builds the C API and the documentation. It allows Prosody functions to be invoked like this: 

	Prosody::Error e = chan.replay_start()
		.type(Prosody::kSMDataFormatALawPCM)
		.speed(50);
	if (e) {
		// handle the error
	}

where chan is an object of type Prosody::Channel.

Note: this is not an official Aculab API and is not supported by Aculab in any way.

Basic architecture

Objects

A typical Prosody API function, such as sm_replay_start() can be considered to operate on one object using a variety of parameters. In the C API, the object is specified in a field in the function's parameter structure. This field has a name which is the same as the kind of object. These are the types of objects used in the API:

C type C++ type Field name API areas covered
tSMCardId Prosody::Card card or card_id Generic API
tSMChannelId Prosody::Channel channel Generic API, Speech API, Data communications API
tSMEventId Prosody::Event eventId Generic API
tSMModuleId Prosody::Module module or module_id or mod_id Generic API, Speech API
tSMPathId Prosody::Path path signal path API
tSMRTCPHandId Prosody::Rtcphand rtcphand RTP API
tSMTDMrxId Prosody::Tdmrx tdmrx Generic API
tSMTDMtxId Prosody::Tdmtx tdmtx Generic API
tSMVidplayId Prosody::Vidplay vidplay Video API
tSMVidrecId Prosody::Vidrec vidrec Video API
tSMVMPrxId Prosody::Vmprx vmprx RTP API
tSMVMPtxId Prosody::Vmptx vmptx RTP API

For example, the sm_replay_start() function has a tSMChannelId field called channel in its parameter structure, so this is the object it operates on. Therefore the C code: 

	tSMChannelid chan;
	SM_REPLAY_PARMS rpp;
	...
	rpp.channel = chan;
	...
	... sm_replay_start(&rpp) ... etc

becomes in C++: 

	Prosody::Channel chan;
	...
	... chan.replay_start() ... etc

The API function name in C starts with the sm_ prefix to help avoid conflicts with user-defined functions. In C++ this is unnecessary, because namespaces provide a better way to do it. All the Prosody identifiers are defined in the Prosody namespace, guaranteeing that they cannot cause conflicts.

Object Lifetime

Construction of one of the C++ objects does not cause the underlying Prosody object to be allocated - the Prosody function must still be called. For example, the code: 

	Prosody::Channel chan;

does not allocate a Prosody channel - it merely constructs an object which can manage a Prosody channel. To cause allocation you must use: 

	chan.alloc_placed()

However, when one of the C++ objects is destroyed, with two exceptions, any underlying Prosody object is freed. For example, for both of these cases: 

	{
	 Prosody::Channel chan;
	}

and 

	Prosody::Channel chan;
	... chan.alloc_placed() ...
	...
	... chan.release() ...

the destruction of chan has no further effect. However in this case: 

	{
	 Prosody::Channel chan;
	 ... chan.alloc_placed() ...
	 ... code which does not release chan ...
	}

the destruction of chan performs sm_channel_release() to free the underlying Prosody channel.

The first exception to this rule for destructors is that the Prosody::Card destructor does not free the tSMCardId.

The other exception is that the Prosody::Event destructor does not free the tSMEventId if it was supplied to the constructor, but it does free it if it was allocated with a create() method. Therefore in: 

		// given tSMEventId ev
	Prosody::Event e1(ev);
	Prosody::Event e2;
	... e2.create(kSMChannelSpecificEvent, chan) ...
	Prosody::Event e3;
	... e3.create(kSMAnyChannelEvent) ...
	Prosody::Event e4;
	... e4.createnonidle(kSMChannelSpecificEvent, chan) ...

the event ev will not be freed unless e1.free() is used, whereas all of e2, e3, and e4 guarantee to free their underlying tSMEventId objects if they have not yet been freed when they are destroyed.

Parameters

In the C API, most functions are passed their parameters by using a pointer to a structure, which must be set to all zero bytes (typically by memset()) before use. This is to allow extra parameters to be added to API functions without requiring changes to application code. Any extra field added to the structure is initialised to zero, so the value zero can be used to represent the behaviour before adding the field and all applications which were written before the extra parameter was added will continue to work as they did before. In C++, this can be achieved without needing the caller to manage the parameter structure. In C++ the setup of the parameter structure looks like this: 

	Prosody::Channel chan;
	...
	chan.replay_start()
		.type(Prosody::kSMDataFormatALawPCM)
	        .sampling_rate(8000)
	        .volume(-3)
	        .speed(70)

The operation (here replay_start()) returns an anonymous object which collects the parameters. The anonymous object implements a set of methods, one for each possible parameter, whose names are the names of the parameter fields defined in the C API. Any parameters not explicitly set default to zero. Parameter fields which return values (marked with /* out */ in the documentation) are the addresses of where the output is to be put. For example, sm_replay_status() fills in the status field in its parameter structure. In the C++ API it looks like this: 

	Prosody::Channel chan;
	enum Prosody::kSMReplayStatus sts;
	...
	chan.replay_status()
		.status(&sts)
	...

If an output parameter is not specified, the value generated for that parameter is not stored anywhere.

Prosody errors

Each Prosody function in the C API returns an error code, with the value zero indicating no error. In the C++ API the functions return an object of type Prosody::Error, which has an implicit conversion to int providing the error code. It also helps catch a very common programming error - not testing the return value of a Prosody function. It does this by printing an error message (on stderr) and aborting the program if a Prosody error is not checked. There are two ways a Prosody error can be checked:

  • Using the conversion to int
  • Using the conversion to bool

Usually a Prosody API function is checked for error using the conversion to bool, like this: 

	Prosody::Error e = chan.replay_status().status(&sts);
	if (e) {
		// report the error somewhere
		// take recovery action
	}

If the error object is destroyed before its value is used (which happens when either one of the implicit conversions is used or when it is copied into another error object), then its destructor prints to stderr complaining that a Prosody error has been ignored and calls abort(). This greatly helps to find the occasional use of a Prosody API function where the error code is not being tested, as it reports the problem whenver the function is used - not just when the function returns an error and ignoring that error causes an obscure problem later.

For testing and debugging, or for situations where you want to show that it's completely hopeless trying to cope with an error, it's possible to indicate that it's OK to ignore an error. This is done by the ok() method. For example: 

	Prosody::Error e = chan.release();
	e.ok();		// ignores the error

Note that this is not the same as: 

	chan.release().ok();		// incorrect

which tries to invoke the ok() method on the anonymous object used to collect parameters.

When the Prosody function is called

The preceeding section suggests when a Prosody function actually gets invoked. It's when the anonymous structure which has been collecting parameters is converted into an object of type Prosody::Error. Consequently, if it is not converted, the Prosody function is not called. For example: 

	...
	chan.replay_start()
		.type(Prosody::kSMDataFormatALawPCM);	// Oops!
	...

To help catch mistakes whereby the parameters are prepared, but the function is not called, if the anonymous structure is destroyed before being used, its destructor prints a complaint on stderr and calls abort(), so the above example will abort the program if it gets run.

Sample code

Some examples are provided to demonstrate and allow testing of the C++ API.

demo.cpp
Very simple example showing only the allocation of a channel and an event.
demoreplay.cpp
Basic replay example. A channel is allocated, used for one replay, and released.
demofile.cpp
A more complex example. A number of channels are allocated. Each is used for both a replay and a recording. The replays each play a file once, while the recordings are stopped after a delay, and finally, all resources are freed and the program exits. This example also uses the EventSet mechanism to allow a worker thread to process record and replay operations while the main thread controls the starting and stopping of the operations.

The pathtest test program is written in C++ and uses this API extensively.
