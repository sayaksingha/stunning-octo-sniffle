ASSP: Timestamp checks on the validity of packets

Introduction

Notation

For a packet, P:

  • P.TXTS is the TXTS field sent in that packet (as extended by the HIGHTIME option)
  • Tx(P) is the time of transmission of P as measured at the transmitter
  • Rx(P) is the time of reception of P as measured at the receiver

General

Since the maximum delay through the network is assumed to be MSL, if two packets are sent at the same time: 

	Rx(A) - MSL <= Rx(B) <= Rx(A) + MSL
or	-MSL <= Rx(B) - Rx(A) <= MSL

Checks using TXTS

For two packets, A and B, delay measured at the receiver may differ because of different delays in transit. The maximum difference at the receiver occurs when B is delayed by almost MSL and A is not delayed: 

	Rx(B) - Rx(A) < Tx(B) + MSL - Tx(A)

while the minimum occurs in the opposite case: 

	Rx(B) - Rx(A) > Tx(B) - Tx(A) - MSL

which gives this: 

	Tx(B) - Tx(A) - MSL < Rx(B) - Rx(A) < Tx(B) + MSL - Tx(A)
	- MSL < (Rx(B) - Rx(A)) - (Tx(B) - Tx(A)) < MSL

We check packets as they arrive, so Rx(B) >= Rx(A). The time differences on which this relies are only measured to limited accuracy, so the check required is derived in TXTS check and is: 

if dTXTS < 0,
	-MSL < dRx / Ermin - dTXTS / Etmax
	dRx / Ermax - dTXTS / Etmax > MSL
if dTXTS > 0,
	-MSL < dRx / Ermin - dTXTS / Etmin
	dRx / Ermax - dTXTS / Etmin < MSL

As an optimisation to avoid division, this can be re-written as: 

if dTXTS < 0,
	-MSL * Ermin * Etmax < dRx * Etmax - dTXTS * Ermin
	dRx * Etmax - dTXTS * Ermax > MSL * Ermax * Etmax
if dTXTS > 0,
	-MSL * Ermin * Etmin < dRx * Etmin - dTXTS * Ermin
	dRx * Etmin - dTXTS * Ermax < MSL * Ermax * Etmin
If the check fails, the packet is alien, otherwise it is valid. When valid, it is fresh if B.TXTS > A.TXTS. and stale if B.TXTS < A.TXTS. If B.TXTS == A.TXTS packet B may be either fresh or stale, and we cannot tell from the TXTS field.

In fact, there is one more factor to take into consideration: the time values A and B are discrete, so there is rounding error. If a time value X, is within a limit of the true time, T or R for transmitter and receiver respectively: 

	T <= X < T+et
and	R <= X < R+er

Then the test becomes: 

	dT - et - er - MSL < dR < dT + et + er + MSL
	-(et + er + MSL) < dR - dT < et + er + MSL

While it seems obvious that the normal choice of scaling for TXTS values would be one where et = er = 1, there may be circumstances (such as mobile devices with variable clock rate) where the precision is better than the accuracy, leading to a larger value of e. Greater precision means that the fixed size time fields wrap sooner, so the precision should be as low as possible. However, the RTT cannot be measured to a better precision than the timestamps, so the precision should be as high as necessary for sufficiently good RTT measurement. Obviously, no measurement can be better than the accuracy of the clock, so the precision used should be no higher than the best accuracy expected.

Check TXTS

	deltaT = B.TXTS - A.TXTS; // taking into account HIGHTIME
	deltaR = Rx(B) - Rx(A);
	dRdT = deltaT - deltaR;
	if (dRdT < -(et + er + MSL)) return ALIEN;
	if (dRdT > et + er + MSL) return ALIEN;
	if (deltaT > 0) {
		// further checks on fresh packets
		return FRESH;
	} else if (deltaT < 0) {
		// further checks on stale packets
		return STALE;
	} else {
		return UNKNOWN;	// but not ALIEN
	}

Limitations on TXTS check

The TXTS check is limited by the accuracy of the clocks used. Assuming a linear error, x of our clock ticks are (1 + E)*x ticks of the transmitter's clock, where E is the factor by which the transmitter's clock is fast. This error causes the difference B.TXTS - A.TXTS to compute: 

	(1 + E) * Tx(B) - (1 + E) * Tx(A)
	(1 + E) * (Tx(B) - Tx(A))
	(1 + E) * dT
	dT + E * dT

so the dR - dT value is wrong by the same amount. If this is big enough, all valid packets will be rejected. This occurs when 

	E * dT = et + er + MSL
	dT = (et + er + MSL) / E     if E > 0
	dT = -(et + er + MSL) / E     if E < 0

Consequently, if we have a transmitter and receiver, each with clocks accurate to about 50 ppm, and every established connection will receive packets with gaps of less than about 248 days, then the TXTS check is correct without further modification. This could be done by sending the high bits in an option. Since this value is only needed every N clock ticks, it could be sent only when necessary.

Effectiveness of the TXTS check

If a packet is received with a random value in TXTS, what is the probablility that it will be accepted by the check?

It is obviously the number of TXTS values that pass the check divided by the number of possible TXTS values. It may appear that the number of possible TXTS values is infinite, since as many high bits as necessary are sent in HIGHBITS options. However, since the high bits of the TXTS field are sometimes deduced rather than being explicit, a packet with no HIGHTIME option and a random TXTS field has a probability of passing the TXTS check. Even if a HIGHTIME option is present, when the packet has been sent by a malicious attacker, the probability is about the same, since the HIGHTIME value is often easily predicted. The probability of a random value passing the TXTS check is the size of the valid range, divided by 2^32 (because the HIGHBITS are not guaranteed to be checked). 

	dT - et - er - MSL < dR < dT + et + er + MSL
	dT < dR + et + er + MSL
	dR  - et - er - MSL < dT
	dR  - et - er - MSL < dT < dR + et + er + MSL

So the range of values is 2 * (et + er + MSL) wide. This is a time. so we can express the 2^32 clock ticks as a time and calculate the probability:

Checks using REFTS

The REFTS values sent are TXTS values which have been received. If we receive two packets, A and B, in that order, we can check the validity of B. If A.REFTS == B.REFTS, then the value is valid. This is because the REFTS value must be a value we sent, and which was received at the remote. Even if we have sent values later than A.REFTS they may not have arrived, so it is still valid to receive the value A.REFTS. If B.REFTS and A.REFTS differ then they must be values from two packets, P and Q, which we sent such that A.REFTS == P.TXTS and B.REFTS == Q.TXTS. Since we cannot receive a TXTS value back in a REFTS field until after we have sent it, we have either: 

	A.REFTS == P.TXTS < B.REFTS == Q.TXTS <= Rx(B)
or	B.REFTS == Q.TXTS < A.REFTS == P.TXTS <= Rx(A) <= Rx(B)

depending on whether P or Q was sent first. We will consider these cases separately.

A.REFTS == P.TXTS < B.REFTS == Q.TXTS <= Rx(B)

No re-ordering

In this case P may have been sent arbitrarily far into the past, and its TXTS value may have been used many times since then. However the last time that it could have been used is just before Q arrived, so this is the latest time at which A could have been sent, which is no later than Tx(Q) + MSL, and therefore the last time that we could have received A is Tx(Q) + MSL * 2: 

	Rx(A) <= Tx(Q) + 2 * MSL
	Rx(A) <= Q.TXTS + 2 * MSL
	Rx(A) - 2 * MSL <= B.REFTS <= Rx(B)
	A.REFTS < B.REFTS <= Rx(B) && Rx(A) - 2 * MSL <= B.REFTS <= Rx(B)

Double re-ordering

This is where P was sent before Q, but they were re-ordered in the network. The remote sent B before A, and those were also re-ordered, so A arrives first and quotes the older TXTS value. Therefore: 

	Tx(P) <= Tx(Q) <= Tx(P) + MSL
	Tx(B) <= Tx(A) <= Tx(B) + MSL

A quotes the TXTS value from P, so it must have been sent after P arrived, which is after Q arrived, so the earliest A can have been sent is after Q arrived, which is after Q was sent: 

	Tx(Q) <= Rx(A)
	Q.TXTS <= Rx(A)
	B.REFTS <= Rx(A)
	A.REFTS < B.REFTS <= Rx(A) <= Rx(B)

Also, the last time at which B could have been sent was before P arrived, which was before Tx(P) + MSL. Therefore the last time it could have arrvied was Tx(P) + 2 * MSL. 

	Rx(B) <= Tx(P) + 2 * MSL
	Rx(B) <= A.REFTS + 2 * MSL
	Rx(B) - 2 * MSL <= A.REFTS
	Rx(B) - 2 * MSL <= A.REFTS < B.REFTS <= Rx(A) <= Rx(B)

B.REFTS == Q.TXTS < A.REFTS == P.TXTS <= Rx(B)

P and Q have been re-ordered

In this case Q must have been sent first, so the latest it can have arrived is at Tx(Q) + MSL. Since they were re-ordered, P must have arrived before this, but it cannot have arrived before it was sent: 

	Tx(P) <= Tx(Q) + MSL
	P.TXTS <= Q.TXTS + MSL
	A.REFTS <= B.REFTS + MSL

Also, A must have been sent after P arrived, so the earliest it can arrive is: 

	Tx(P) <= Rx(A)

and the latest it can have been sent is just before Q arrived, which is no later than Tx(Q) + MSL, so the latest it can have arrived is after a further MSL: 

	Rx(A) <= Tx(Q) + 2 * MSL
	Tx(P) <= Rx(A) <= Tx(Q) + 2 * MSL
	P.TXTS <= Rx(A) <= Q.TXTS + 2 * MSL
	B.REFTS <= Rx(A) <= B.REFTS + 2 * MSL
	B.REFTS - 2 * MSL <= Rx(A) - 2 * MSL <= B.REFTS
	B.REFTS - 2 * MSL <= Rx(A) - 2 * MSL <= B.REFTS < A.REFTS <= Rx(B)

A and B have been re-ordered

Again, Q must have been sent first. It can have been sent an arbitrarily long time ago, with B being sent before P arrived. Since the latest P can have arrived is Tx(P) + MSL, and B can take at most MSL in transit: 

	Rx(B) <= Tx(P) + 2 * MSL
	Rx(B) <= P.TXTS + 2 * MSL
	Rx(B) <= A.REFTS + 2 * MSL
	B.REFTS < A.REFTS <= Rx(B) <= A.REFTS + 2 * MSL
Combining all of these we have four possibilities: 
	Fresh: A.REFTS < B.REFTS <= Rx(B) && Rx(A) - 2 * MSL <= B.REFTS <= Rx(B)
	Stale: Rx(B) - 2 * MSL <= A.REFTS < B.REFTS <= Rx(A) <= Rx(B)
	Stale: B.REFTS - 2 * MSL <= Rx(A) - 2 * MSL <= B.REFTS < A.REFTS <= Rx(B)
	Fresh: B.REFTS < A.REFTS <= Rx(B) <= A.REFTS + 2 * MSL

If all tests fail, a packet is alien: if a fresh test and a stale test pass, we cannot know whether it is fresh or stale until other fields are examined.

It's also possible to verify that the result of the TXTS check is consistent with the conclusion drawn by the REFTS check.

It may be useful to keep a record of the last TXTS value we sent. This means that if a connection is idle for a long time, we will reject any bogus REFTS value since the last TXTS we sent.

Note that a clock which ticks every microsecond will wrap a 32-bit counter after one hour, eleven minutes, 34.967296 seconds. If a connection has been idle for a long time, the checking must be careful to avoid rejecting valid packets.

Checks using ACK

ACK values must be sent in non-decreasing order and cannot acknowledge data not yet sent. This allows us to check that for packets A and B: 

	deltaT = B.TXTS - A.TXTS;
	acked = B.ACK - A.ACK;	// see section on ACK checks
	if (deltaT > 0) {
		if (acked < 0) return ALIEN;
		if (B.ACK - TCB.SND.UNA > TCB.SND.NXTSEQ - TCB.SND.UNA) return ALIEN;
		return STALE;
	} else if (deltaT < 0) {
		if (acked > 0) return ALIEN;
		return FRESH;
	}
	return FRESH;

Obviously, this performs no check if the TXTS values are the same, since we cannot tell the order of transmission. This test is also somewhat dangerous when a packet is stale. If we are transmitting very quickly, so that the ACK value has wrapped within the last MSL, then we might get an old packet with a numerically larger ACK value. This can only happen if more than 2^31 different values are sent in a period of MSL, but it is possible. Furthermore, the processing of a fresh packet updates TCB.SND.UNA to the ACK value received, so it is redundant to compare with A.ACK.

The recommended check is: 

	deltaT = B.TXTS - A.TXTS;
	if (deltaT > 0) {
		if (B.ACK - TCB.SND.UNA > TCB.SND.NXTSEQ - TCB.SND.UNA) return ALIEN;
		return STALE;
	}
	return FRESH;

This check is incorporated into the check shown in the above section describing the TXTS checks.

Effectiveness of the ACK check

If a packet is received with random values in TXTS and ACK, what is the probablility that it will be accepted by the ACK check? Firstly, there is a probability of 0.5 that it will be accepted because deltaT is zero or negative. In this case unsequenced options will be ignored, but any data might be used. If deltaT is positive, the probability of B.ACK being valid depends on the number of unacknowledged packets, UP, outstanding, and is (UP + 1)/ 2^32. The best case occurs when there are no outstanding packets, which is the typical case half of the time (because typically only one end is sending data, while the other is only sending acknowledgements).

Checks using SEQ

While there are restrictions on which SEQ values can be sent, they are not very useful to validate packets. Assume we offer a fixed size window, W. When a packet arrives with SEQ value S, we know that the remote receiver must have seen our acknowledgement of S - W. Therefore: 

	Rx(S) >= Tx(ACK = S-W) >= Rx(S-W)

However, to check this, we would need to save for MSL either the time at which we first sent an ACK for each SEQ value, or the arrival times of all packets which carried a new SEQ value. This could be an arbitrarily large amount of data, so it is impractical, but it would be useful to have at least some criteria for classifying packets as alien based on their SEQ value, since a connection which has been idle for more than MSL can reject nearly all SEQ values. One way of doing this would be to record the earliest arrival time of each of the last W SEQ values, then if no new SEQ values are received for MSL, values are stale if: 

	RCV.NXT - W < S < 0

fresh if: 

	0 <= RCV.NXT < S + W

and alien otherwise.

Generating replies

In some circumstances an incoming packet must cause a reply to be generated using only the information in the incoming packet. One example of this is an alien packet, which requires us to generate a RST. If we generate a packet, OUT in reply to a packet, IN, we should set: 

	OUT.SEQ = IN.ACK;
	OUT.ACK = IN.SEQ;
	OUT.TXTS = IN.REFTS;
	OUT.REFTS = IN.TXTS;

A reply generated by this method may not pass the checks described above. In particular, the TXTS check is likely to fail because value is guaranteed to be at least RTT out of date, since it is IN.REFTS, which was an old value of TXTS. Consequently, when a packet is received and classified as alien, a special check must be made to see if it is a reply to the last packet sent. If so, it is fresh. This is necessary to clear half-open connections. If a half-open connection occurs with the open end using a large transmit window, its packets will provoke reset replies, but the replies will be ignored as each is a reply to a packet older than the latest. However, as part of loss recovery, the window must close, and when it reaches the value of one, the next reset generated will close the connection. Note that this is only guaranteed to work if the estimated RTT is at least as long as the true RTT, so it is important that excessive packet loss either cause the connection to close or cause the estimate of the RTT to increase.
