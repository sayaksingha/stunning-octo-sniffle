Asymmetric High Load Protocol Requirements

General architecture

We have a server and clients. The clients control operations on the server by sending commands and bulk data. There is a range of real-time requirements which vary depending on exactly what operations are being performed, what stage the operations have reached, and which command is being sent. We want to be capable or running at high load. This includes load on the network, meaning that we want to operate successfully when total traffic is a large percentage of maximum throughput, and load on the client and server CPUs. Clients are expected to handle thousands of simultaneous connections and the server will contain multiple CPUs with both shared and private memory, which means that one server can handle many clients.

Consequences of network load

To allow operation at high network load, we want to minimise the number of packets sent and their size. Note that the overhead for sending a packet is fairly high, so the number of packets is generally much more important than their size.

Consequences of real-time variation

If fast delivery is important, the sender must know very soon whether or not to retransmit. To avoid unnecessary acknowledgements, we generally want to defer acknowledging data in the hope that we can send it with some data. Unfortunately, deferred acks cause the sender to perceive a longer round trip time (RTT), making it impossible to re-transmit quickly. The protocol must, therefore, make provision for different criteria to allow a transmitter to detect loss quickly for some traffic while not requiring excessive acks for traffic which does not require it.

Consequences of CPU load

To allow operation at high CPU load, we want to minimise the CPU time required. This requires us to minimise the time to process each packet as well as the number of packets processed.

One way to avoid wasting CPU time in the receiver is to prevent the protocol from delivering data in a manner which requires it to be reassembled. For example, if a value is represented as a 32-bit word, we don't want part of that word to arrive in one packet and part in the next as this means either the data from the second packet must be appended to the data in the first, or the code accessing the value has to reconstruct it from the two pieces. Since the data layout is application dependent, the most practical way to ensure the receiver gets data conveniently segmented is for the transmitter to respect boundaries generated by the transmitting application. This only requires the protocol to avoid splitting data into separate packets and doesn't prevent it aggregating data into fewer packets.

Consequences of asymmetry

When a client sends a command which generates a response, the response does not need to be acknowledged, since the client is expecting it and will re-transmit the command if no response is received. This means it is highly desireable to avoid sending an acknowledgement. This always saves at least one packet, as derived in Expected number of transmissions.

Consequences of large number of connections

Traditionally, protocols have used port numbers to address connections within a single host. For incoming connections, each addressible service is identified by a well-known port (or, possibly, a small number of well-known ports). We will need to allow clients to address parts of the server (because the CPUs in the server don't share all memory) and have many connections to each. This means the protocol must have good addressibility.

Other

It seems obvious that, especially when implementations have been deployed, ways will be found to improve the protocol. Therefore mechanisms should be provided which allow it to be extended without violating the other requirements.

Although the protocol is designed for situations in which it consumes a large proportion of the network capacity and the hosts' processing ability, for testing and debugging it is very valuable to ensure that it works across the Internet. Even though the bandwidth may be too low for normal operation and the latency too high, the ability to run the same protocol allows systems to be remotely tested and debugged instead of requiring access to a host which is local to the test system.

It may seem obvious, but it must be possible to implement the protocol! This means that it must be practical to write an implementation on systems which have existing IP stacks which cannot be modified.

Conclusions

The requirements result in these principles:

  • Avoid unnecessary traffic
  • Permit varied timeliness for re-transmissions
  • Minimise CPU time for processing. This applies to each location:
    • transmitting application
    • transmitting host
    • intermediate routers
    • receiving host
    • receiving application
  • Avoid breaking up chunks of data (as seen by application)
  • Permit Extensions
  • Allow operation across low bandwidth, high latency links.
  • Good addressibility
  • Must be implementable

These lead us to the protocol itself.
