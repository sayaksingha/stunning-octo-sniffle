An ASSP implementation

This documents an implementation of the protocol described in A Protocol for Asymmetric High Load.

The general architecture used is that there are 'connections' handled by the protocol. When creating a connection, you specify how the protocol uses external facilities such as its network connection and timers. In C++ this would use abstract base classes, but in C it's a bit more complicated, and will be explained later. You start off the protocol by arranging for there to be a path to remote ASSP implementations which can carry ASSP packets. To act as a client, you then create a TCB and initiate an ASSP connection by calling assp_connect(). To act as a server, you wait for incoming packets, and pass them to the packet handler. When you use assp_connect(), you specify the CID value to identify the connection. These values are intended to have predefined meanings, so the value chosen may select which particular connection at the server will receive the new incoming connection.

When a connection has been established, your nexttx() method is called, which may return a packet to send. To get an empty packet, call assp_txpacket() specifying the TCB and maximum data size you need. Then fill in the data. The packet allocated by assp_txpacket() is a structure with two fields you must use: datastart is a pointer to the start of the data. You must copy your data into the packet starting at this location. You must then set the dataend field to point to the location after the data. There is another field which you may use: rawend. This is the maximum permitted value for dataend. This may be more than you asked for. Packets that you return from your nexttx() method must not be empty except for the last one which uses the ASSP_F_EOF flag. A packet passed into assp_abort(), however, may be empty.

Whenever you have data to send, you call assp_txready() to indicate that there is data ready. The protocol implementation will then call your nexttx() callback when appropriate to collect the data. Finally, if you need to discard the TCB completely, you call assp_tcb_dtor.

Abstract base classes in C

The essential feature of an abstract base class is that it defines an interface to an arbitrary variety of objects. While C cannot express this directly, it can be expressed in a reasonably straightforward manner. First, we define a struct which contains only pointers to the methods required. This is essentially the vtbl which C++ maintains behind the scenes. Then we define a struct containing just two items: a pointer to this vtbl, and a pointer to the object data. Since we're defining an abstract class, we have no idea what that object data will contain, so we define it as a named struct but don't provide any definition of the struct. In C this allows us to use pointers to the struct, and have them type-checked, but prevents accidentally trying to dereference them.

TIMEQUEUE

Here's an example of an abstract TIMEQUEUE class taken from the protocol implementation: 

#include "timefn.h"

typedef struct timequeue_impl TIMEQUEUE_IMPL;

struct timequeue_vtbl {
	void (*start)(TIMEQUEUE_IMPL *tq, void (*fn)(void *p), void *p, ABSTIME when);
	long (*next_timer_mS)(TIMEQUEUE_IMPL *tq);
	void (*dtor)(TIMEQUEUE_IMPL *tq);
};

typedef struct {
	struct timequeue_vtbl *vtbl;
	TIMEQUEUE_IMPL *tqi;
} TIMEQUEUE;

This is quite a simple class, as it has only three methods. The last, dtor(), is the destructor; the first, start(), inserts a timer into the queue; and the second, next_timer_mS() runs any timers which have already expired and then returns the number of milliseconds until the next timer is due. Given an object tq in a class derived from TIMEQUEUE, you invoke the methods like this: 

	tq.vtbl.start(tq.tqi, fn, p, tomorrow);
	lm = tq.vtbl->next_timer_mS(tq.tqi);

where fn is a function to be run, p is the parameter to pass to it, tomorrow is when to run it.

Of course, since this is an abstract class, we need a derived class to provide an implementation. Here is an example (as used in the protocol implementation). First its header: 

typedef struct timer {
	struct timer *next;
	ABSTIME when;
	void (*fn)(void *arg);
	void *arg;
} TIMER;

struct timequeue_impl {
	TIMER *first;
};

void timequeue_lin_init(TIMEQUEUE *tq, TIMEQUEUE_IMPL *tqi);

This uses a simple linear linked list to record the timers, so it only needs a pointer to the first one, while each pending timer needs to record the parameters passed to start() as well as a pointer to the next. When we want to create an object of this derived class, we do this: 

	#include "timequeue_lin.h"

	...

	TIMEQUEUE tq;
	TIMEQUEUE_IMPL tqi;
	timequeue_int_init(&tq, &tqi);
	...

The header we included gives the contents of TIMEQUEUE_IMPL so that the compiler can allocate the space for it. Of course this also means you could access the fields directly, since C doesn't have private fields in structs, but you simply avoid doing that! If you use only the TIMEQUEUE type in a section of code, then that code does not depend on the particular timequeue class being used - just like when you refer to methods in an abstract class in C++. For example: 

	#include "timequeue.h"
	...

	int do_something(TIMEQUEUE *tq)
	{
	 ...
	 if (timeout_required()) {
	 	tq->tqi->start(tq->tqi, timefn, obj, tmo);
	 }
	 ...
	}

Note that, unlike in C++, a single source file cannot create objects in two different classes which have been derived from the abstract class since including timequeue_thing.h and timequeue_otherthing.h in the same file would produce two conflicting definitions of the struct timequeue_impl.

The implementation of the linear-list TIMEQUEUE is like this: 

#include "timequeue_lin.h"

typedef struct timequeue_impl TQI;

static void starttimer(TQI *tqi, void (*fn)(void *arg), void *arg, ABSTIME when)
{
 TIMER *tim = malloc(sizeof(*tim));
 ...
}

static long next_timer_mS(TQI *tqi)
{
 for (;;) {
	TIMER *t = tqi->first;
	long nx;
	if (!t) return -1;
	nx = time_rel2longmS(time_until(t->when));
	if (nx > 0) return nx;
	tqi->first = t->next;
	t->fn(t->arg);
	free(t);
 }
}

static void dtor(TQI *tqi)
{
 if (tqi->first) abort();	// bug: queue not empty
}

static struct timequeue_vtbl timequeue_lin_vtbl = {
	starttimer,
	next_timer_mS,
	dtor,
};

void timequeue_lin_init(TIMEQUEUE *tq, TIMEQUEUE_IMPL *tqi)
{
 tq->vtbl = &timequeue_lin_vtbl;
 tq->tqi = tqi;
 tqi->first = 0;
}

It starts by defining a synonym for TIMEQUEUE_IMPL to make the name shorter in this file. Then we have the implementation of the methods, followed by the vtbl, and the 'constructor'. The constructor must have a name which specifies what sort of derived class it produces. This is so that a program which uses more than one derived class doesn't have more than one function with the same name. Since this is the only identifier visible outside this file, the methods can only be invoked on objects prepared by the constructor, so the struct timequeue_impl parameter they get will always be of the type they expect.

TCBPATH

The TCBPATH abstract base class specifies how the protocol implementation interfaces to the network which carries its datagrams to the remote protocol implementation. It contains these methods: 

	int (*validate_cookie)(TCBPATH_IMPL *path, TCB *tcb, MD5_STREAM *msp, U8 *cp, U8 *endp);
	void (*generate_cookie)(TCBPATH_IMPL *path, TCB *tcb, MD5_STREAM *msp, U8 *cp);
	void (*make_keycode)(TCBPATH_IMPL *path, TCB *tcb, U8 *sp, U8 *ep, U8 *op );
	PACKET *rxalloc(TCBPATH_IMPL *path, unsigned maxrx);
	void (*rxfree)(TCBPATH_IMPL *path, PACKET *pkt);
	void (*netsendpkt)(TCBPATH_IMPL *path, char *data, char *end);
	void (*netgotpkt)(TCBPATH_IMPL *path, char *data, char *end);
	void (*path_dtor)(TCBPATH_IMPL *path);

The cookie handling needs to be handled differently for each type of transport because it needs to use the endpoint addresses as part of its calculation to protect against cookies being obtained from one address and used from another.

An interface may use a special pool of receive buffers. This is particularly likely at the lowest levels of a protocol stack, where the interface hardware may have a chain of waiting receive buffers and automatically fill them via DMA as packets are received. When such buffers become available again (i.e. when the data they carry is delivered) they may be put directly back on the buffer chain to save having an overhead of allocating and freeing receive buffers. There may also be separate pools for each interface, to prevent a flood of packets on one interface starving all the others. Consequently, when a receive buffer is no longer needed, the rxfree method is called to free it. This may be done by ASSP itself (e.g. when a packet is just an ACK and carries no data), or may be done by the application (e.g. when a packet containing data has been received, delivered, and is no longer needed).

The details of these methods are:

int (*validate_cookie)(TCBPATH_IMPL *path, TCB *tcb, MD5_STREAM *msp, U8 *cp, U8 *endp);
Check a received cookie. tcb is the connection's TCB, msp is an MD5 stream initialised with internal ASSP data, cp points to the first octet of the cookie received, and endp points to the first octet after the cookie. The return value is non-zero to indicate that the cookie is valid, zero if it is invalid.
void (*generate_cookie)(TCBPATH_IMPL *path, TCB *tcb, MD5_STREAM *msp, U8 *sp);
Generate a cookie in response to a cookie request. tcb is the connection's TCB, msp is an MD5 stream initialised with internal ASSP data, and cp points to the first octet of the space to put the generated cookie,
U8 *(*make_keycode)(TCBPATH_IMPL *path, TCB *tcb, U8 *sp, U8 *ep, U8 *op);
Make a keycode. sp points to the first octet of the cookie, ep points to the first octet after the cookie, and op points to the first octet of the space to put the keycode. Returns a pointer to the first octet after the keycode.
PACKET *rxalloc(TCBPATH_IMPL *path, unsigned maxrx);
Allocate a PACKET for reception. maxrx is the maximum number of octets that the buffer must be capable of holding. On return, the rawstart field points to the place in the buffer where incoming data should be put, and the dataend field points to the byte after the last byte allocated for incoming data in the buffer. When data is put into the buffer, these fields must be adjusted to indicate the amount of data actually present. rawstart must be advanced over any header (e.g. Ethernet IP, and UDP headers) and dataend must be reduced to point to the first byte after the user data received.
void (*rxfree)(TCBPATH_IMPL *path, PACKET *pkt);
Free a receive buffer that was allocated with rxalloc().
void (*netsendpkt)(TCBPATH_IMPL *path, char *data, char *end);
Send a packet. data points to the first octet of data to be sent, and end points to the first octet after the data to be sent.
void (*netgotpkt)(TCBPATH_IMPL *path, char *data, char *end);
Indicate a packet has been received (for collecting statistics). data points to the first octet of data received, and end points to the first octet after the data received.
void (*path_dtor)(TCBPATH_IMPL *path);
Destroy the path.

TCBPATH - for simulation

The pathsim implementation of TCBPATH is used in simulation. It provides a model of the path between two endpoints.

TCBPATH - pathnet

The pathnet implementation of TCBPATH uses UDP/IP to carry ASSP datagrams. Its constructor is: 

void pathnet_init(TCBPATH *tcbpath, TCBPATH_IMPL *pathnet, int sock);

where sock is the UDP socket to use.

Connection types

This implementation supports multiple types of connection, where a connection type is defined by the actions relating to transmission. It is defined using a virtual function table: 

typedef struct assp_conn ASSP_CONN;

struct assp_tcb_vtbl {
	int (*sof)(ASSP_CONN *cnx);
	void (*rx_peek)(ASSP_CONN *cnx, unsigned ofs, PACKET *pkt);
	void (*deliver)(ASSP_CONN *cnx, PACKET *pkt);
	void (*eof)(ASSP_CONN *cnx);
	void (*stopped)(ASSP_CONN *cnx);
	void (*closed)(ASSP_CONN *cnx);
	TXPACKET *(*nexttx)(ASSP_CONN *cnx, int *flags);
	void (*txack)(ASSP_CONN *cnx, PACKET *txp, int acked);
};

The ASSP user defines one or more of these tables, and the ASSP_CONN type can be different for each. This permits, for example, unrelated ASSP protocols to be run on different network interfaces, or even over different types of network (e.g. IP and IPX).

These functions are called as described here:

int (*sof)(ASSP_CONN *cnx);
Invoked at start-of-file. For connections that you initiated (by calling assp_connect()), this is called when the connection receives a cookie. In this case the return value is ignored. For incoming connections, it is called when a valid SYN is received. The return value indicates whether or not to accept the connection. Return zero to refuse the connection, non-zero to accept it. The cnx parameter is the value that you passed to assp_tcb_init(). After this is invoked, data can be delivered (through rx_peek() and deliver()), though it does not affect transmission.
void (*rx_peek)(ASSP_CONN *cnx, unsigned ofs, PACKET *pkt);
Invoked for each received data packet when it first arrives, regardless of whether or not it is the next expected packet. The cnx parameter is the value that was passed to assp_tcb_init(). ofs is the number of packets between this one and the one due to be reported by deliver(), so it is non-zero when a packet arrives out of sequence. pkt points to the packet. This method gives an application an opportunity to peek at received data before it is delivered. If an application wants to handle all received data out of sequence, it can use this method and use invocations of deliver() only to free the packets; if it wants to handle some data in sequence and some out of sequence, it must maintain its own record of which packets have already been handled. On entry to this method, the datastart field of the packet points to the first octet of user data and the dataend field points to the first octet after the user data, and the values of these fields are not used or modified by ASSP from this point onwords, so the application can freely modify them itself.
void (*deliver)(ASSP_CONN *cnx, PACKET *pkt);
Invoked to deliver data in sequence. The cnx parameter is the value that was passed to assp_tcb_init(). pkt points to the packet, which is one already reported by calling the rx_peek() method. deliver() is invoked exactly once for each received packet and is invoked on the packets in order of their sequence numbers. When it is invoked, ownership of the PACKET passes from ASSP to the application, which must call the path rxfree() method when the packet is no longer needed.
void (*eof)(ASSP_CONN *cnx);
Invoked when end-of-file is reached. The cnx parameter is the value that was passed to assp_tcb_init(). After this is invoked, no further data can be delivered, though it does not affect transmission.
void (*stopped)(ASSP_CONN *cnx);
Invoked when the connection is no longer capable of transporting data. The cnx parameter is the value that was passed to assp_tcb_init(). After this is invoked, no further transmission or reception of any type can be performed. However the protocol implementation continues to use the TCB for its own purposes.
void (*closed)(ASSP_CONN *cnx);
Invoked when the implementation has completely finished using the TCB. The cnx parameter is the value that was passed to assp_tcb_init(). When this is invoked, the TCB can be deleted or re-used as desired by the application.
PACKET *(*nexttx)(ASSP_CONN *cnx, int *flags);
Invoked when the protocol is capable of sending more data. The cnx parameter is the value that was passed to assp_tcb_init(). You may either return 0 (the null pointer) to indicate that you do not have any data for transmission, or a PACKET which contains the next packet of data to be sent. The flags parameter is a bitmask of flags associated with the packet. It is initialised by ASSP to 0 or ASSP_F_MUSTACK and should be modified as necessary by the nexttx() handler. The possible flags are:
ASSP_F_ACKLESS
This data is a response to a higher-level request and the implementation may assume the it can leave the remote host to trigger re-transmissions.
ASSP_F_FASTACK
This data is time-critical. An instant acknowledgement is required so that the shortest possible timeout can be used.
ASSP_F_EOF
There is no more data to follow after this packet.
ASSP_F_MUSTSEND
This flag is provided by ASSP and means that it believes that it must send a packet anyway (e.g. because an acknowledgement must be sent). This can be used to optimise data transfer.

Note that it is incorrect to specify both ASSP_F_ACKLESS and ASSP_F_FASTACK.

void (*txack)(ASSP_CONN *cnx, PACKET *txp, int acked);
Invoked when the fate of txp is known. If the packet has been acknowledged, then acked is non-zero: otherwise the packet may have been lost (e.g. the connection has been reset). The cnx parameter is the value that was passed to assp_tcb_init().

Preparing a connection

The first step in preparing a connection is invoking assp_tcb_init(). It's prototype is: 

void assp_tcb_init(TCB *tcb, ASSP_CONN *cnx, TIMEQUEUE *tq, TCBPATH *tcbpath, struct assp_tcb_vtbl *vtbl);

where the parameters are:

TCB *tcb
The TCB to be prepared
ASSP_CONN *cnx
An arbitrary pointer which will be passed to the methods in the vtbl.
TIMEQUEUE *tq
A timer queue. This is derived from the TIMEQUEUE abstract base class.
TCBPATH *tcbpath
A path though which ASSP communicates. This is derived from the TCBPATH abstract base class.
struct assp_tcb_vtbl *vtbl
The vtbl defining the methods which ASSP must invoke for this connection.

Getting connected as a server

There are two general strategies for handling multiple connections. The first is to predefine a number of TCBs each with a particular CID. This has the advantage that incoming connection requests are handled just like any other packet: you find the TCB with the matching CID value and invoke assp_handle_rx() on it. Alternatively, you can have just a single TCB devoted to listening. In this case, when you cannot find the TCB which corresponds to an incoming packet, you make the CID of the listening TCB equal to that of the received packet and invoke assp_handle_rx(). When your sof() method is called and you are about to return non-zero, this TCB has started handling a connection, so if it is you special listening TCB, you need to create a new one for listening. This approach allows an arbitrary number of connections to be handled at the cost of a bit more processing. You also need to remove or re-use TCBs which the protocol has finished using and are reported through your closed() method.

Getting connected as a client

A client calls assp_connect() to initiate a connection to a server. When the protocol is ready to make the connection (i.e. when it has obtained a cookie from the server), it will call your txready() method. If you supply a packet, this will be the packet which carries the SYN. Otherwise the implementation will allocate its own packet to carry the SYN. Obviously this will cause your sof() and allsent() methods to be invoked when the connection has opened. The txready() method will normally be invoked also. This won't happen until the server gives us permission to send data which is not guaranteed to happen when the connection opens, but it would be very unusual for a server to accept a connection if it was not ready to receive data on it.

If the connection cannot be opened, your stopped() method will be invoked.

Operating connections

Every open connection is waiting for one of three possible events:

  • a timeout
  • reception of a relevant incoming packet
  • data becoming available to send

This means you typically have a loop waiting for these three events. You know when the next timeout is due by calling the next_timer_mS() method on the TIMEQUEUE being used by the open TCBs (you can share a single TIMEQUEUE between any number of TCBs). If you have separate threads potentially generating these events, then you need to ensure that mutexes are used appropriately to protect the shared data (TCB and TIMEQUEUE). You need to hold the same mutex whenever you call any API function on the same TCB, or on any other TCB which shares the same TIMEQUEUE.

When a received packet arrives, you need to find the appropriate TCB and call assp_handle_rx() on that TCB pasing in the received packet. Note that when you do this, ownership of the packet is transferred to ASSP, which becomes responsible for arranging for it to be freed when no longer needed. You can find the CID value in an incoming packet by calling assp_rx_cid() on that packet. Note that the protocol may not free the buffer for an arbitrarily long time since it may hold sequenced data which must wait for a packet with a lower sequence number. Equally, when a received packet is handled, this may fill a gap in the sequence numbers triggering the freeing of many old packets.

When you have more data to send, you should call assp_txready() to indicate that data is ready. ASSP guarantees that it will call your nexttx() method:

  • once when the connection is established, either after you call assp_connect() or after sof() accepts an incoming connection
  • once more every time your nexttx method returns a packet to be sent
  • once after you call assp_txready()

This means that if you have all the data available before the connection (for example, the connection has been set up to send a file), you need not call assp_txready() at all, as nexttx() will keep being called. Otherwise, each time you return 0 from nexttx() you must use assp_txready() to resume sending when more data becomes available. However, when testing and debugging, note that ASSP may call nexttx() even if assp_txready() has not been used since nexttx() last returned a packet.

Closing connections

Orderly closure

The orderly closure of a connection starts when you return a packet from your nexttx() method with the ASSP_F_EOF flag. This packet will carry the FIN option, and can carry data just like a normal transmit packet.

When the remote end sends EOF, this eventually causes your eof() method to be invoked. No further data can be received after this, but this has no effect on your transmission of data. You can keep the connection open arbitrarily long after having seen eof.

When both ends have sent EOF, the connection closes. At this time your stopped() method is invoked. There is a timer protecting the connection resources for a period after this, to prevent any packets from this connection interfering with future connections. This means that the TCB remains in use by the protocol for a while. When the protocol has finished using the tcb, your closed() method is invoked, which may invoke assp_tcb_dtor(), or initiate re-use of the TCB. If necessary, assp_tcb_dtor() will block for a period of time to guarantee that this protection timeout is preserved.

Abrupt closure

A connection may be abruptly closed. This can occur for several reasons: invocation of assp_abort(), persistent failure of the link to the remote party, violation of the protocol by the remote party, unrecoverable network errors, or notification that the remote party has ceased to function. When the closure is locally initiated, a RST packet may be sent. In other circumstances (for example, upon detection of the total failure of the underlying communications link), no packet is sent. In all cases, all data in transit is lost and the connection proceeds as if orderly shutdown had occurred, starting with the stopped() method being called. Note that abrupt closure may result in some packets which were reported by rx_peek never being delivered.

Checking connections (keepalive)

The ASSP connection relies on an underlying network connection provided by a TCBPATH. In addition to failures which cause abrupt connection failure, there may be circumstances in which there is a suspicion that the connection may have a problem and needs to be tested. The function assp_validate() can be called at any time to cause ASSP to ensure that the remote ASSP is provoked into sending a response.
