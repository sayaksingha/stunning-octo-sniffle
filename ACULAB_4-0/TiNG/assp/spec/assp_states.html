Protocol states for ASSP

The protocol states are:

  • CLOSED - no connection exists
  • WAIT-COOKIE - waiting for a reply carrying a cookie to allow a connection to be completed
  • ESTABLISHED - ready to transfer data
  • FIN-WAIT - a FIN has been sent, so we continue reception until we receive a FIN but we cannot send more data
  • CLOSE-WAIT - a FIN has been received, but we can continue sending as we have not sent a FIN
  • LAST-ACK - a FIN has been both sent and received and we are waiting for all outstanding packets to be acknowledged
  • RST-WAIT - a RST has been sent and we are waiting for it to be acknowledged
  • TIME-WAIT - FIN has been both sent and received - we are waiting a safe time to allow stale packets to drain from the network before letting the connection go idle

The protocol always starts in the CLOSED state.

Note that the TIME-WAIT state can be truncated at the server end if the cookie used to open this connection would not be capable of re-opening the connection and the server knows that the client has received an ACK it sent acknowledging the client's FIN (which it could tell from the REFTS field in an incoming packet). This is because the client would only be permitted to re-use the connection if it retains the sequence numbers, which protects against all stale packets apart from replay of the cookie.

Events

The events which are handled by the protocol are:

  • connect()
  • abort()
  • send EOF
  • packet arrival
  • timeout

State transitions

Some protocols (such as TCP [RFC 793] and RDP [RFC 908]) support opening of a connection from both ends simultaneously. ASSP does not allow this. Instead, every connection is opened asymmetrically, with one end initiating the open and the other responding. This allows us to remove the ACK bit in the header, since without symmetric open every packet can carry an acknowledgement number.

connect()

If we are creating the TCB (i.e. not on the transition from TIME-WAIT), generate random numbers for each of SND.NXTPKT, SND.NXTSEQ, RCV.NXT, RCV.RECENT. Otherwise we will continue to use the existing ones, which protects against old packets from the previous connection, so we can safely truncate the TIME-WAIT state.

Send GET-COOKIE.

Go to WAIT-COOKIE.

abort()

If we are in CLOSED, RST-WAIT or TIME-WAIT, do nothing. If we are in WAIT-COOKIE, go to TIME-WAIT. In other states, send a RST and go to RST-WAIT.

send EOF

Generate a FIN packet and add to the outbound sequenced packet queue. Go to FIN-WAIT or LAST-ACK depending on whether we are in ESTABLISHED or CLOSE-WAIT.

get cookie

We must be in the WAIT-COOKIE state, (otherwise the packet is stale and can be ignored). Send a SYN quoting the cookie. Go to ESTABLISHED.

get SYN

Note that a SYN is alien unless it quotes a valid cookie.

In the CLOSED state, if it's a valid SYN, set up our sequence numbers based on its header (i.e. SEQ from its ACK, ACK from its SEQ, etc). Send an ACK. Go to ESTABLISHED.

In TIME-WAIT, if the SYN is a valid continuation, go to ESTABLISHED, otherwise ignore it. A valid continuation uses SEQ, ACK, TXTS, and REFTS numbers which continue from those previously used. A SYN is ignored if it is not a valid continuation because the client will re-try, eventually trying after the TIME-WAIT state has been left.

If we are in the ESTABLISHED or FIN-WAIT states, if it is a duplicate of the original SYN, it's stale so we send an ACK. Otherwise it's acceptable but is a protocol error, so we abandon the connection, report an error, send RST and go to TIME-WAIT. Note that the cookie protection makes it extremely likely that it is a duplicate SYN.

process FIN

Note that FIN is a sequential option so this processing is performed when the user attempts to read data and gets the last of the data that includes the FIN.

In the ESTABLISHED state, go to CLOSE-WAIT. In FIN-WAIT, go to LAST-ACK (note that we may instantly proceed to TIME-WAIT). In other states, it's a protocol error, so we send a RST and go to TIME-WAIT.

get RST (other than a RST reply)

Ignore it if we are in CLOSED, or TIME-WAIT. If we are in RST-WAIT, stay in RST-WAIT, sending a RST reply unless the incoming RST had the ACKLESS option. Otherwise, discard unacknowledged data, setting SND.UNA to SND.NXTSEQ, discard received data not yet delivered, setting RCV.NXT to the SEQ value in the RST packet, and abandon the connection and go to TIME-WAIT, sending a RST reply unless the incoming RST had the ACKLESS option.

get RST reply

This can only happen in RST-WAIT, since that is the only state in which there is an outstanding RST to which there might be a reply. Discard unacknowledged data, setting SND.UNA to SND.NXTSEQ, discard received data not yet delivered, setting RCV.NXT to the SEQ value in the RST packet, and abandon the connection and go to TIME-WAIT.

got ACK for all outstanding packets

In LAST-ACK our FIN has been acknowledged, go to TIME-WAIT. (Note that this condition may already be true when we enter LAST-ACK and therefore we would instantly pass through to TIME-WAIT). Otherwise we handle this ACK just like any other ACK.

Other operations

When the connection moves to ESTABLISHED, the local user is notified (this may be by an API function returning or similar means). When the connection has entered the ESTABLISHED state until EOF has been sent, data may be written. An attempt to read after the connection has reached CLOSE-WAIT or LAST-ACK will indicate that there is no further data (e.g. EOF).
