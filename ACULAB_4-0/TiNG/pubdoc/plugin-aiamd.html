Introduction

This note describes the additional functionality provided by ProsodyS AI AMD (AI-Driven Answering Machine Detection), how ProsodyS AI AMD is installed and configured, and how an application accesses it through the TiNG API.

A standard installation of ProsodyS, among other functions, allows an application to categorise (or classify) signals as live speakers or answer machines using a simple duration based algorithm. ProsodyS can be augmented with a more complex AI assisted classification algorithm through installation of the ProsodyS AI AMD plugin package using the Aculab Installation Tool (AIT).

In order for this functionality to be available to applications, AI AMD specific ProsodyS feature licences must be installed . Contact your Aculab account manager for more information on obtaining the ProsodyS AI AMD plugin AIT package together with enabling licences.

AI AMD Overview

The signal classification algorithm analyses an 8KHz sampled signal fed to a Prosody channel input passing over any call progress tones until start of speech is detected. It then acquires as much of the subsequent signal as is required for the AI AMD model set in use, and then invokes classification processing on the acquired signal. Currently, two model sets are provided in the AI AMD package:
  • us_1750 - requires 1.75s segment of post start of speech signal
  • us_1500 - requires 1.5s segment of post start of speech signal
The AI AMD algorithm limits the amount of speech it requires in order to be able to rapidly notify the application of the classification outcome (allowing the classification response time measured from start of speech to notified outcome to be under 2s).

Selection of the 1.75s model gives more accurate results but has a longer classification response time.

Normally a three way classification occurs:

  • signal is considered to be live speaker
  • signal is considered to be a machine response
  • signal does not contain any speech (optional timeout)
An option exists to request live speaker signal to be "best effort" subclassified into:
  • likely to have come from residential live speaker
  • likely to have come from business live speaker
The AI AMDs algorithm's ability to distinguish between residential and business speakers is limited to what it can achieve with the 1.5s or 1.75s length signal segments that it uses.

Further options enable classifier to report a signal as coming from a fax machine, or starting with a special information tone (SIT) sequence, or busy tone sequence, or matching a standard announcement prefix.

There is an option for classification to generate a timeout event if an input signal does not contain any speech. The timeout is reset each time a call progress or ringing signal is detected in the signal prior to start of speech, restarting at the end of such a tone. An application may choose to implement its own additional overall timeout and cancel classification if that expires (for example if a call is not answered).

Detection of beginning and end of tones will be notified to application as signal is processed up to the point where speech is first detected.

Accuracy of classification can be improved with additional contextual information linked to signalling, in particular the length of the "ring time" delay which occurs before a call is answered. If this information is available to the application (for example by analysis of "SIP 180 Ringing" notifications), it should be passed into the algorithm using the signalling hint mechanism described below.

ProsodyS requires additional CPU resources to run the AI AMD signal classification algorithm, these need to be configured to meet the classification capacity required - see below for details.

Aculab software version requirements

Support for ProsodyS AI AMD plugin requires TiNG library 2.52.18 (m1495) or later.

Support for AI AMD timeout requires TiNG library 2.53.0 (m1496) or later.

Support for additional AI AMD configuration data requires TiNG library 2.53.6 (m1502) or later.

Installation and licensing

The AI AMD software is distributed in the AIT package "ProsodyS_AIAMD_Plugin", once your AIT account has had this package added, it may be installed in the normal way using the Aculab Installation Tool (AIT).

The resulting installed ProsodyS Plugin will be located in the usual ProsodyS "ps_plugins" subdirectory under $ACULAB_ROOT/bin64 (Linux) or %ACULAB_ROOT%\bin\amd64 (Windows).

A ProsodyS AI AMD feature licence key must be obtained from Aculab. Once the feature licence key has been obtained it can be installed using the Aculab configuration tool (ACT) or the command line LicenceAdmin tool and will supply the purchased number of AI AMD licence instances. Each licence instance permits an addition AI AMD task to run concurrently.

ProsodyS AI AMD licences have a "Feature ID" of 3, you can check the number of feature licences installed using the LicenceAdmin's tool "Display licence information" option.

There is also the option of purchasing an uncapped licence for AI AMD where the number of AI AMD tasks that may be run concurrently is not licence limited - contact Aculab for details.

Using AI AMD with TiNG API

Three API calls in the TiNG API are used to interact with the ProsodyS AI AMD plugin to categorise signals:

  • sm_catsig_listen_for()
  • sm_catsig_signalling_hint()
  • sm_get_recognised()

The first two calls set up an ongoing categorisation task. Once the signal has been categorised, a channel recognition event (kSMEventTypeRecog) will occur and the result may then be obtained using sm_get_recognised().

Setting up a categorisation task

The function sm_catsig_listen_for() must be invoked with catsig_alg_id parameter set to kBESPCatSigAlgLiveSpeakerPlugin in order for AI AMD plugin algorithm to be used for categorisation.

The parameters catsig_config_data and catsig_config_length may be used to specify an optional text buffer of specified length containing a comma separated list of additional classification parameters as follows:

  • model=<model> - explicitly specify model set to be used for classification (must be one of models explicitly or implicitly configured in aculab.config)
  • business - request classifier to try and distinguish live responses as being from business or from residential responders
  • fax - enable classification of signals as fax machines
  • sit - enable classification of signals as starting with special information tone (SIT)
  • sam - enable classification of signals as starting with standard announcement prefix
  • busy - enable classification of signals as starting with busy or fast busy tone sequence
See also Diagnosing classification problems for additional parameter items that can be specified for classification diagnosis.

Example parameter text buffers: 

  model=us_1500
  model=us_1500,business,fax,sit
The initial hint (sm_catsig_listen_for() parameter catsig_hint_param) and the subsequent hint (API call sm_catsig_signalling_hint()) are used to notify availability of contextual "ring time" information to the classification algorithm (see algorithm overview).

If no reliable ring time information is going to be available, then the initial hint parameter catsig_hint_param should be set to zero and sm_catsig_signalling_hint() should not be called.

If ring time information is immediately available from signalling, then the initial hint parameter catsig_hint_param should be set with that value, specified in milliseconds.

If it is known ring time information will subsequently be available from signalling, then the initial hint parameter catsig_hint_param should be set to -2 and when the ring time information becomes available, it should be supplied as a millisecond value using sm_catsig_signalling_hint().

If it is uncertain ring time information will subsequently be available from signalling, then the initial hint parameter catsig_hint_param should be set to -1 and subsequently:

  • if it becomes apparent explicit ring time information will not be available, a subsequent hint value of zero should be provided - the algorithm will then try and infer ring time from observed input signal
  • if it becomes apparent ring time information will be available, a subsequent hint value of -2 should be provided, and then when available, ring time should be supplied as millisecond value in subsequent hint
For applications using the Aculab call control API the following sequences illustrate use of initial and subsequent hint parameter being invoked as signalling events occur:
  1. No ringing before 200 OK
    • EV_MEDIA (initial hint -1)
    • EV_CALL_CONNECTED (subsequent hint 0)
  2. Ringing before 200 OK
    • EV_OUTGOING_RINGING (initial hint -2)
    • EV_MEDIA
    • EV_CALL_CONNECTED (subsequent hint RT in ms)
  3. Ringing after media event
    • EV_MEDIA (initial hint -1)
    • EV_OUTGOING_RINGING or EV_PROGRESS (subsequent hint -2)
    • EV_CALL_CONNECTED (subsequent hint RT in ms)
In sequence 1, it is initially not certain what will follow EV_MEDIA (so initial hint is -1), then when subsequent EV_CALL_CONNECTED occurs it is apparent that explicit ring time information will not be available through analysis of signalling (so subsequent hint of 0 is set).

In sequence 2, given the initial EV_OUTGOING_RINGING event, it is immediately apparent it will be possible to supply ring time information (so initial hint is -2), and then when EV_CALL_CONNECTED occurs, the time difference between this and the occurrence of EV_OUTGOING_RINGING should be supplied in milliseconds as a subsequent hint.

In sequence 3, it is initially not certain what will follow EV_MEDIA (so initial hint is -1), then subsequent EV_OUTGOING_RINGING or EV_PROGRESS indicates it will be possible to supply explicit ring time information (so subsequent hint of -2 is set), and when EV_CALL_CONNECTED eventually occurs, the time difference can be supplied as in sequence 2 (time between EV_OUTGOING_RINGING and EV_CALL_CONNECTED).

Cancelling a classification task

An ongoing categorisation task can be cancelled by invoking sm_catsig_listen_for() with the catsig_alg_id parameter set to kBESPCatSigAlgLiveSpeakerPlugin and abort_catsig_alg set to non-zero value.

Obtaining classification outcome

A channel recognition event kSMEventTypeRecog occurs when the AI AMD algorithm has classified a signal or a timeout has occurred. A subsequent call to sm_get_recognised() will return kSMRecognisedCatSig set in type field, the algorithm id set in param0 and a classification code in param1 field. The following classification codes are defined:

  • 0 - Machine response
  • 1 - Live speaker
  • 2 - Start of tone
  • 3 - End of tone
  • 4 - Timeout
  • 5 - Live business speaker
  • 6 - Fax machine
  • 7 - SIT
  • 8 - Busy or Fast Busy
If standard announcement prefix matching is configured, then sm_get_recognised() can also return a classification code starting from 100, indicating matching of an announcement in ProsodyS configured SAM file.

Standard announcement prefix matching

It can be useful to identify a signal as starting with audio that exactly matches the beginning of a known recording of a standard announcement message (with matching relying on the waveform uniqueness of even a short segment of an announcement and the end-to-end fidelity of automatic digitally recorded announcement signals). For this kind of matching, ProsodyS can be configured with a standard announcement model (or SAM) file prepared from recorded audio of a small number (up to 16) of standard announcements. If the signal being classified has an almost exactly identical waveform prefix to one of the signals compiled into the SAM file, then the signal will be considered classified and a classification code reflecting the announcement matched will be returned by sm_get_recognised().

SAM files are created using tool samfilegen. 

    samfilegen [flags]
Running the tool without any flags lists the contents of an existing SAM file.

Running the tool with -c flag creates a new SAM file. 

    samfilegen -c myannouncements.sam

Running tool with -a flag adds an announcement prefix to existing SAM file with parameters as follows: 

    samfilegen -a <wav> <offset> <count> <min-score> <sam-file>
where: 
    <wav> - is WAV (A-Law, mu-law or 16-bit 8Khz sampled) file containing announcement audio
    <offset> - is numeric offset in samples indication where announcement starts in file
    <count> - is number of samples that need to be exactly matched (must be multiple of 256)
    <min-score> - is numeric score on how exact the match needs to be to trigger classify event
The offset specified should be a sample position just before first speech utterance in the specified WAV file and the count should be between 2048 and 8192 samples long (256ms to 1024ms), with longer lengths improving matching selectivity but costing more CPU to compute. Typically a length of 4096 samples (512ms) gives good results.

The min-score parameter specifies how exact the matching needs to be to trigger classification, the higher the value, the more strict the match must be. For typical use a min-score value of 50 is suggested. For call environments where some missing prefix samples or other damage might be present in match candidate signals a lower min-score may be appropriate. Selection of too low a min-score value can cause false matches to occur, using a min-score value below 30 is unlikely to result in a useful level of selectivity.

Level 3 tracing (see Diagnosing classification problems) can be used to view the match scores obtained for specimem signals and help selection of a suitable min-score.

The name of the generated SAM file needs to be specified as a plugin configuration attribute.

The SAM file used by ProsodyS can be updated while ProsodyS is running by using the samfilegen tool with the -u flag. For example the following command will copy "myannouncements.sam" to ps_plugins psaiaimd/models subdirectory, update plugin configuration to specify new SAM file, and stimulate ProsodyS instance having IP address 127.0.0.1 and security key "mykey" into using updated SAM. 

    samfilegen -u 127.0.0.1 mykey myannouncements.sam

Plugin configuration

Attributes for the classification algorithm may be set in an "aiamd" section in "aculab.config" XML configuration file (see MAN1170 ProsodyS User guide section 4.6): 

    <card type="prosodys_v3">
       ...
       <aiamd>
          ... AI AMD attributes
       </aiamd>
       ...
    </card>
If no attributes are set, then the default configuration of:
  • default and only model available is "us_1750"
  • ProsodyS is provisioned with 2 classification worker threads
The following attributes may be set:
  • model - specifies comma separated list of available models - with default (used on zero length catsig_config_data) being first in list
  • classifiers - number of classifier threads (see Provisioning classification CPU resources)
  • verbose - cause classifier information to be dumped into ProsodyS log for diagnosis purposes
  • samfile - specify a SAM file containing a set of standard announcements located in ps_plugins psaiaimd/models subdirectory.
  • sensitivity - adjust classifier threshold (lower value biases classification of uncertain cases to err more toward machine, higher value to err more toward live) - default 0.5
A simple configuration just setting classifier thread count and model list would be: 
    <aiamd model="us_1500,us_1750" classifiers="3"/>

Provisioning classification CPU resources

ProsodyS must dedicate a number of threads for running classification jobs, a suitable number of these need to be created for the system capacity required. The default is to assign 2 such threads, this number can be adjusted through setting the classifiers plugin configuration attribute.

Selection of the number of threads will depend on platform performance and CPU cores available. Aculab support can give advice on determining provision for a given system scenario.

Diagnosing classification problems

For diagnosing individual classification tasks, extra items may be included in the comma separated parameter string specified when sm_catsig_listen_for() is invoked. The additional parameters will cause classification related information to be logged to the ProsodyS log and (when requested) recordings of the initial speech utterance to which classification was applied to be created in the ProsodyS log directory.

The additional items that may be specified in the sm_catsig_listen_for() comma separated parameter string are:

  • id=<idname> - when records created in ProsodyS log, they will include specified identifier, for example id=call2239
  • record - create recordings of initial speech - 16 bit PCM little endian samples - in directory where ProsodyS log is located, file name will include <idname> if id was specified
  • trace=<level-digit> - show more detailed information about classification signal processing, the level-digit (0-5) controls amount of detail (levels 3 and over can create large amounts of trace affecting system performance under load)
  • sensitivity=<frac> - set sensitivity for this task to be value between 0.1 and 0.9
Level Detail
0 No classification information logged
1 Only successful standard announcement matches logged
2 As 1 and also AMD/live classification outcomes
3 As 2 but also include scores for all standard announcement matches (failed matches too)
4 As 3 but show more detailed information regarding AMD/live classification
5 As 4 with some extra plugin activity logging

If the AI AMD plugin configuration attribute "verbose" is set non-zero in the ProsodyS configuration file, then recording and level 5 tracing will occur for every classification task (irrespective of comma separated string settings used in sm_catsig_listen_for).
